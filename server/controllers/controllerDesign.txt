CONTROLLERS RULES :
Good instinct to slow down and build the mental model — once this clicks, you'll write controllers fast without copying patterns blindly. Let me go through it in order: what a controller is, the full request flow, the anatomy of a controller function, and then the actual decision-making — which method to reach for and why.

## 1. Where a controller sits

**Route → Controller → Model → Database**, with middleware layered in before the controller runs.

```
Client (browser/Postman)
   │  HTTP request: method + URL + headers + body
   ▼
Express Route (routes/lawyerRoutes.js)
   │  matches the URL pattern to a handler
   ▼
Middleware (auth check, validation, rate limiting...)
   │  runs BEFORE the controller, can reject early
   ▼
Controller (controllers/lawyerController.js)
   │  the actual "what happens" logic
   ▼
Model (models/LawyerProfile.js)
   │  Mongoose translates JS calls into MongoDB queries
   ▼
MongoDB Atlas
   │  data comes back
   ▼
Controller formats it → res.json(...)
   ▼
Client receives the response
```

Your mental model is correct, with one refinement: **the route doesn't do logic, it just points**. Look at how thin a route file should be:

```js
// routes/lawyerRoutes.js
router.get('/', lawyerController.getLawyers);
router.get('/:id', lawyerController.getLawyerById);
router.patch('/:id', auth, requireRole('lawyer'), lawyerController.updateLawyer);
```

The route says *"when this URL+method combo hits, run these functions in this order."* Everything that decides *what happens* — reading the DB, checking permissions, shaping the response — lives in the controller (or middleware, for cross-cutting stuff like auth).

**Rule of thumb**: if you're tempted to write `if (req.method === 'GET')` inside one giant handler, stop — that's a sign you need separate route entries, not branching logic.

## 2. The anatomy of a controller function

Every Express controller has the same signature:

```js
const controllerName = async (req, res, next) => {
  // body
};
```

- `req` — everything about the incoming request
- `res` — how you send a response back
- `next` — hands off to error-handling middleware if something goes wrong

Inside, almost every controller follows the same five-step shape, in this order:

```js
const updateLawyer = async (req, res, next) => {
  try {
    // 1. EXTRACT — pull out what you need from the request
    const { id } = req.params;
    const { bio, hourlyRate } = req.body;

    // 2. VALIDATE — is the input even usable?
    if (hourlyRate !== undefined && hourlyRate < 0) {
      return res.status(400).json({ message: 'hourlyRate cannot be negative' });
    }

    // 3. AUTHORIZE — is THIS user allowed to do THIS action?
    //    (often pushed into middleware instead, see below)

    // 4. TALK TO THE DATABASE — the actual work
    const lawyer = await LawyerProfile.findByIdAndUpdate(id, { bio, hourlyRate }, { new: true });

    // 5. RESPOND — shape and send the result
    if (!lawyer) return res.status(404).json({ message: 'Not found' });
    return res.status(200).json(lawyer);

  } catch (err) {
    // 6. HAND OFF ERRORS — never let an unhandled throw crash the server
    next(err);
  }
};
```

Once you see this 1-2-3-4-5 shape, writing a new controller stops being "what do I write" and becomes "fill in each numbered slot for this specific case."

**Where does data come from in step 1?** This is the part people mix up:

| Source | When it's used | Example |
|---|---|---|
| `req.params` | Values embedded in the URL path | `/lawyers/:id` → `req.params.id` |
| `req.query` | Filters/options after `?` | `/lawyers?minRate=500` → `req.query.minRate` |
| `req.body` | Data sent in a POST/PATCH payload | `{ "name": "..." }` → `req.body.name` |
| `req.user` | Attached by your auth middleware, not the client | `req.user.userId`, `req.user.role` |

A quick way to decide which one a new field belongs in: **params identify a specific resource, query filters/sorts a collection, body carries data to create or change something, and `req.user` is identity you never trust the client to send directly.**

## 3. Deciding *which* controllers you need

You don't invent controllers randomly — you derive them from your resources (nouns: lawyers, bookings, messages, payments, users) crossed with the operations that make sense for each (CRUD-ish verbs). Ask, for each resource: **can someone create it, read one, read many, update it, delete/cancel it?** Not every resource needs all five.

Look at how this played out for CaseLeeto:

- **User/Auth** → no generic CRUD, because auth has its own vocabulary: `register` (create, but with hashing), `login` (read + verify, not a real "GET").
- **LawyerProfile** → `getLawyers` (read many), `getLawyerById` (read one), `updateLawyer` (update). No `createLawyer` as its own endpoint — a profile gets created implicitly during registration, and no `deleteLawyer` because the product doesn't need lawyers to be deletable, just editable.
- **Booking** → `createBooking`, `getBookingById`, `getBookings` (read many, scoped), `updateBookingStatus` — a narrower "update" than a generic PATCH, because status changes follow a state machine (pending→confirmed→completed/cancelled), not free-form edits.
- **Message** → only `getMessagesByConversation` as a REST controller. Creating a message doesn't get a controller at all — it happens over a Socket.IO event instead, because it's real-time by nature.
- **Payment** → `createOrder`, `verifyPayment` — again not generic CRUD, because payments follow a specific lifecycle (create → get provider confirmation → mark paid), not "edit any field."

**The pattern**: start from generic CRUD as a checklist, then narrow it wherever the resource has its own real-world lifecycle (bookings have a status machine, payments have a verification step, messages are event-driven). If an operation doesn't map cleanly to Create/Read/Update/Delete, give it its own verb-named controller (`verifyPayment`, `updateBookingStatus`) instead of forcing it into a generic `update`.
